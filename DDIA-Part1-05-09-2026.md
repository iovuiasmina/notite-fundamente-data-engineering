In perioada 2010, NoSQL etse ultima tentativa de a depasi modelul relational, pentru a-l "detrona"

NoSQL - nu face referire la o anumita tehnologie, fiind initial folosit ca un simplu hashtag(#) catchy pentru un Twitter destinat unei intalniri in legatura cu DB open source + distributed + nonrelational(2009) - insa, denumirea a fost atat de catchy incat un nr impresionant de DB sunt asocitate acum cu *#NoSQL* a carui interpretare a devenit: Not Only SQL

##### NoSQL = Not Only SQL

Exista mai multe motive in spatele adoptarii bazelor de date NoSQL inclusiv:
- nevoia de *scalabilitate mai mare* decat cea pe care o pot atinge cu usurinta bazele de date relationale, inclusiv *seturi de date foarte mari sau randament de scriere foarte ridicat*
- *o preferinta larg raspandita pentru software-ul gratuit si open source fata de produsele comerciale de DB*
- *operatiuni de interogare specializate care nu sunt bine suportate de modelul relational*
- frustrarea fata de restrictivitatea schemelor relationale si *dorinta pentru un model de date mai dinamic si expresiv*

Tine foarte mult de aplicatie ce model de date alegi si bineinteles ca variaza enorm de la un software la altul

Exista aceasta idee ca in viitor, DB relatioanle vor fi utilizate alaturi de o varietate mare de Datastores nonrelationale => *polyglot persistence*

Aplicatiile moderne proceseaza totul, de la tranzactii financiare conforme cu ACID la retele sociale bazate pe grafuri, de la fluxuri de senzori in timp real la documente nestructurate => incercarea de a satisface aceste cerinte cu o singura tehnologie de baze de date duce inevitabil la compromisuri in ceea ce priveste performanta, scalabilitatea sau productivitatea dezvoltatorilor

Polyglot persistence - raspuns arhitectural pentru utilizarea strategica a mai multor tehnologii de baze de date intr-un singur sistem; in loc sa forteze toate datele intr-un singur model, aceasta abordare potriveste fiecare set de date cu tehnologia sa optima de stocare

##### Polyglot persistence => > 1 tehnologie de DB + !! un singur sistem

Definitie si principii de baza:
- un singur ecosistem de aplicatii, unde fiecare baza de date este selectata pe baza adecvarii sale pentru caracteristici specifice ale datelor si modele de acces => 
##### recunoaste ca nicio tehnologie de baze de date unica nu poate servi optim toate cazurile de utilizare

Principiile de baza:
- *alinierea tehnologiei si a datelor*: potrivirea tehnologiilor de stocare cu caracteristicile datelor, mai degraba decat fortarea datelor sa se conformeze unui singur model
- *scalabilitate independenta*: permiterea scalarii diferitelor componente in functie de cerintele lor specifice
- *arhitectura evolutiva*: sprijinirea modificarilor incrementale si a adoptarii tehnologiei fara refactorizare la nivel de sistem - practic, o aplicatie modulara, "fiecare cu nasul in oala lui"
- *optimizarea performantei*: valorificarea bazelor de date specializate pentru sarcinile de lucru dorite

Schema ilustreaza conceptul de Polyglot Persistence: 

Componentele principale
- API Gateway / Integration Layer: punctul unic de intrare pentru clienti, primind cererile si redirectionandu-le catre microserviciul responsabil
- Microservices / Modules: fiecare caseta colorata = serviciu independent care gestioneaza o anumita parte a aplicatiei
- Baze de date dedicate (Stocarea):
    - User Service: PostgreSQL (Relational DB)
    - Product Catalog: MongoDB (Document DB)
    - Recommendation Service: Neo4j (Graph DB)
    - User Session: Redis (Key-Value Store)

Provocarile Arhitecturii:
- Data Consistency Challenges:
    - Distributed Transactions: intrucat datele sunt izolate in baze de date diferite, nu mai poti face un simplu TRANSACTION COMMIT pe toate
    - Eventual Consistency: sistemul trebuie sa foloseasca arhitecturi bazate pe evenimente (event-driven, de exemplu Kafka) unde datele se sincronizeaza in timp, nefiind identice in aceeasi milisecunda peste tot
- Data Migration Challenges:
    - Schema Evolution: schimbarea structurii datelor devine complexa pentru ca trebuie sa gestiuni modificari in paralel pe sisteme SQL, NoSQL, memorie si grafuri

Obs: majoritatea aplicatiilor dezvoltate astazi au la baza limbaje de programare orientate obiect => critica comuna a modelului de date SQL: daca datele sunt stocate in tabele relationale, este nevoie de un layer "awkward" de tranzitie intre obiecte - neconexiunea dintre modele se numeste de regula *impendance mismatch* - ce am facut la disciplina Programare 2? => ORM(Object-relational mapping) + Hibernate

Acest "layer awkward" de tranzitie(ORM - Object-Relational Mapping, cum ar fi Hibernate / JPA in Java) - necesar din cauza diferentelor mari dintre:
- modul in care gandeste un *limbaj orientat pe obiecte* si 
- modul in care *stocheaza datele o baza de date SQL*

Principalele 4 diferente structurale care creeaza aceasta problema:

1. Tabele vs. Obiecte - CUM se ORGANIZEAZA datele?
- OOP: datele sunt incapsulate in obiecte complexe care pot contine alte obiecte, liste, seturi sau ierarhii
- SQL (Relational): datele sunt stocate in tabele bidimensionale (randuri si coloane) formate doar din tipuri de date primitive (numere, text, date)

Obs: pentru a salva un singur obiect complex (ex: o "Comanda" care contine o lista de "Produs"), ORM-ul trebuie sa sparga obiectul si sa execute instructiuni INSERT in 2-3 tabele diferite => cand citesti datele, trebuie sa execute JOIN-uri si sa reconstruiasca manual obiectele in RAM...

2. Referinte vs. Chei Straine - CUM se fac LEGATURILE?
- OOP: obiectele se leaga prin referinte directe in memorie
Ex: comanda.getClient().getAdresa();
- SQL: tabelele se leaga prin valori FK si au nevoie de operatii explicite de JOIN

3. Mostenirea (Polimorfismul) NU EXISTA in SQL
- OOP: poti avea o clasa de baza si subclase care o extind
Ex:
class CardBancar extends MetodaPlata { ... }
class Paypal extends MetodaPlata { ... }
- SQL: conceptul de mostenire nu exista...

Obs: pentru a salva aceasta ierarhie in SQL, ORM-ul trebuie sa aplice o strategie din urmatoarele:
- Single Table
- Class Table - clase separate doar cu atributele specifice, PK subclase e FK pentru PK din clasa
- Concrete Table Inheritance - clase separate cu toate atributele - eficient pentru query-uri foarte simple

4. Identitatea - CUM STII ca doua lucruri sunt EGALE?
- OOP: 2 obiecte pot fi egale prin memorie (a == b; imi amintesc aceasta intrebare din cadrul laboratorului de Programare 2 si a fost un challenge care mi-a placut muuult) sau prin continut (a.equals(b))
- SQL: un rand este unic doar daca are PK definita

Reminder: mi-am adus aminte de intrebarea pusa de domnul profesor Dumitriu la cursul/laboratorul de PSI care era ceva de genul: putem avea in DB o tabela fara PK? - avem tendinta sa spunem ca nu, pentru ca mereu, cand facem o tabela, ne dorim sa extragem intr-un anumit format datele sau sa operam cumva asupra lor INDIVIDUAL - cuvantul cheie: INDIVIDUAL, pentru ca intr-o tabela fara PK, putem avea chiar 2, 3, infinit randuri exact lafel - de asta, se foloseste de regula in tabele de log unde nu  avem nevoie sa extragem date INDIVIDUAL - a fost o intrebare si o dezbatere faina atunci

Beneficiile impedance mismatch:
- flexibilitate crescuta: aplicatiile pot utiliza propriile structuri de date, personalizate in functie de cerinte specifice
- performanta mai buna: structurile de date personalizate pot permite o gestionare optimizata a datelor si interogari mai rapide
- dezvoltare mai usoara: dezvoltatorii pot lucra cu API-uri orientate pe obiecte familiare fara a scrie constant interogari SQL

Limitarile impedance mismatch:
- complexitate crescuta: gestionarea maparilor intre doua modele diferite adauga costuri suplimentare de dezvoltare
- risc mai mare de erori: conversiile de date intre structuri pot duce la inconsistente sau mapari incorecte
- functionalitate limitata: unele caracteristici DBMS nu pot fi utilizate pe deplin prin intermediul modelelor orientate pe obiecte, ceea ce duce la o eficienta redusa si la o intretinere mai mare...

- In modelul SQL traditional (anterior SQL:1999), cea mai comuna reprezentare normalizata este plasarea pozitiilor, educatiei si informatiilor de contact in tabele separate cu o referinta de cheie externa la tabelul utilizatorilor
- Versiunile ulterioare ale standardului SQL au adaugat suport pentru tipuri de date structurate si date XML; acest lucru a permis stocarea datelor cu valori multiple intr-un singur rand, cu suport pentru interogare si indexare in interiorul acelor documente => caracteristici acceptate in grade diferite de Oracle, IBM DB2, MS SQL Server si PostgreSQL; tipul de date JSON este, de asemenea, acceptat de mai multe baze de date, inclusiv IBM DB2, MySQL si PostgreSQL
- O a treia optiune este de a codifica locurile de munca, educatia si informatiile de contact ca document JSON sau XML, de a le stoca intr-o coloana text din baza de date si de a lasa aplicatia sa interpreteze
structura si continutul acestuia => de obicei nu puteti utiliza baza de date pentru a interoga valori in interiorul acelei coloane codificate

JSON - mult mai simplu decat XML(multe document-oriented DB suporta acest model: MongoD, RethinkDB, CouchDB, Espresso)

Unii dezvoltatori considera ca modelul JSON reduce nepotrivirea de impedanta dintre codul aplicatiei si stratul de stocare

JSON are o localitate mai buna - toate informatiile relevante sunt intr-un singur loc, iar o singura interogare este suficienta - decat schema din Figura 2-1(pentru obtinerea unui profil, trebuie fie
sa efectuam mai multe interogari, fie sa efectuam o jonctiune multiway dezordonata intre tabelul utilizatorilor si tabelele sale subordonate)

Relatiile one-to-many de la profilul utilizatorului la pozitiile utilizatorului, istoricul educational si informatiile de contact implica o structura arborescenta in date, iar reprezentarea JSON face ca aceasta structura arborescenta sa fie explicita
